First — why this matters

Studios trust us inside their code.

USP co-develops features inside studios' games, and verifies engine features in real productions. We're handed other people's codebases and in both, our value rests on one thing: shipping changes that work, without breaking what already worked.

The Pain

It worked when we handed it off.

Picture a co-dev engagement. We ship a change that looks clean, and everyone moves on.

The fear isn't the feature we shipped. It's the regression: the existing system that quietly broke, in a corner nobody replayed.
The scenario
Embedded in a studio's codebase, we ship what looks like a clean change. The only safety net that it didn't break anything is replaying it by hand.
The regression
Days before the studio's milestone, they hit it: our change quietly broke an existing system. It worked when we left it.
The real cost
Found late, on their timeline, with our name on it.
The Problem

The regression surface only grows

  • Every feature we add to a project is one more thing that can silently break , and it stays breakable for the rest of the engagement.
  • Re-checking it all by hand, every change, scales linearly: more surface → more hours → more chances to miss something.
  • The bottleneck lands on the milestone, exactly when no one can afford to slip.
Each block = something that must be re-verified by hand, every time the project changes →
The Solution

It's just code that tests your code.

Bots that run thousands of checks in milliseconds, automatically, every time someone pushes a change.

No human in the loop Runs on every change Same checks, every release, forever
The Scope

Here's the thing: we often don't even have QA.

Co-dev rarely comes with a dedicated QA team. When we lean on the studio's, they're stretched across their whole game, and our changes wait in the queue.

So the bots are the safety net: always on, nobody to ask
Does it still build? Does the feature still return the right result? Did our change break an existing system? Does the scene still load?
Humans still do the judgment
Is this the right approach for their architecture? Does the integration fit the studio? Is the design sound? Is the studio happy?
So automation isn't replacing testers we don't have, it's the systematic check that runs on every change.
The Toolbox · the kinds of tests, in Unity terms

Three layers, from fast to real

End-to-end / Smoke a few · on real hardware · slowest
Integration · Play Mode dozens · loads a scene, simulates frames
Unit · Edit Mode hundreds · pure logic, no game running · fastest
↑ more realistic & slower  ·  ↓ faster & cheaper, run far more
Rule of thumb: many fast unit tests, fewer integration, a handful of end-to-end.
Unit · Edit Mode
Checks one piece of logic on its own: no scene, no game running. Milliseconds each, so you run hundreds.
damageFor(lvl:10, crit:true) == 250 ✓ 2 ms // just the math
Integration · Play Mode
Loads a real scene and simulates frames: checks the pieces work together.
load Level → simulate jump →
assert player lands, HUD updates
End-to-end / Smoke (BVT)
Runs the actual build on real hardware: does it boot and survive?
build boots → loads main scene ✗ crash // the handoff regression
And the one we live in — Performance & memory

A slowdown should fail the build, like any bug.

We spend our days profiling and optimizing, but the gains quietly erode. The next change adds a few milliseconds; by the next milestone the win is gone.

measure("Town") → avgFrame ≤ 16.6 ms // else fail CI
Set budgets, frame time, memory, draw calls, and let CI check every change. It turns optimization from a recurring firefight into a ratchet that only moves one way.

Recap

The five-minute version

  • Our job is to ship changes that don't break what already worked.
  • Manual re-checking doesn't scale — automated tests run on every change, our safety net even when there's no QA.
  • Layers: fast unit (Edit Mode), some integration (Play Mode), a few smoke — plus performance budgets that fail the build on a regression.
  • The payoff: predictable milestones, trust with the studio, cost that crosses over.
Start small with one smoke test. The whole idea: predictable work now, instead of firefighting later.
